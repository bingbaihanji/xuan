# JFGL 抗锯齿设计（子项目 A）

> 状态：**设计已定，待评审**。本文是子项目 **A（抗锯齿）** 的规格。
> 它的三个下游（B 直线线型、C 图表配色、D 图表观感）都排在它之后，
> 理由见 §3.5——**B 的虚线与圆角接头要用 A 定下的那一条顶点属性**。

---

## 0. 结论摘要

1. **MSAA 能用，但它不是"零成本"，而且只能在构造时配。** 实测（§1）：`msaa=4` 时
   openglfx 确实建了多采样 FBO 并正确 resolve 到 JavaFX，画面完全正确、**拾取不受影响**；
   但 `glReadPixels` 在画布 FBO 上返回 `GL_INVALID_OPERATION` ⇒ **本仓库全部七个像素
   校验器在 `msaa>0` 时立刻全瞎**。所以 `msaa` 默认必须是 0。
2. **解析式 AA 只覆盖"有中心线"的几何**（一切描边 + 图表系列），**填充一律交给 MSAA**。
   分界线不是"解析 vs 非解析"，而是**几何知不知道自己的中心线在哪**（§3.2）。
3. **只需要一条新顶点属性 `vec2 aEdge`**（顶点格式 24 → 32 字节），加图表系列的一个
   varying。**不需要新材质、不需要新渲染器、不需要后处理**（§3.3、§3.4）。
   **两个分量是"横向 + 沿向"**——平头端（`Gc` 现在唯一在用的端帽样式）的端边垂直于线段，
   只靠横向距离描述不了它（§4.1 有完整推导）。
4. **两个开关默认都关**，因此既有 370 条单测与七个校验器**逐像素不变**（§6）。

## 1. 实测事实（2026-09-26，本机）

### 1.1 探针

`example/MsaaProbe.kt`（**探针**，它的去留见 §7.6）。一个进程只测一个采样数，
因为它只能在构造 `GLCanvas` 时给。命令：

```bash
mvn -o -f jfgl-javafx/pom.xml compile exec:exec "-Dexec.executable=java" "-Dexec.classpathScope=runtime" \
  "-Dexec.args=-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -Djfgl.probe.msaa=4 -cp %classpath com.bingbaihanji.jfgl.example.MsaaProbe"
```

**两条互相独立的读数路径**，这是本探针唯一重要的设计：

| 路径 | 做法 | 它读的是 |
|---|---|---|
| **A** | `glReadPixels` 画布 FBO | GL 侧的帧缓冲内容 |
| **B** | JavaFX `node.snapshot()` | **用户眼睛看到的东西**（合成器读那块共享纹理） |

**必须两条都有**，因为第一次跑只做了 A，`msaa=4` 读回**全黑**，看起来像
"MSAA 把渲染整个搞坏了"。是 `GL_INVALID_OPERATION` 这个错误码提示了真相：
**多采样 FBO 上 `glReadPixels` 本身就是非法操作**——那是**读数方式坏了**，不是渲染坏了。
B 路径（完全绕开 `glReadPixels`）否掉了那个结论：圆画得好好的。

> **这条正是本项目那条判据的又一次应验**：怀疑被测对象之前，先怀疑测量本身。

### 1.2 结果

| 读数 | `msaa=0` | `msaa=4` |
|---|---|---|
| `GL_SAMPLE_BUFFERS` / `GL_SAMPLES`（画布 FBO） | `0` / `0` | **`1` / `4`** |
| `GL_MAX_SAMPLES`（本机 GPU 上限） | 32 | 32 |
| 路径 A：`glReadPixels` | 正常（2 种亮度、硬跳变） | **`GL_INVALID_OPERATION`(1282)，读出全 0** |
| 路径 B：圆有没有画出来 | ✅ 在 | ✅ **在**（背景 476761 + 纯白 136870 + 边缘 3633） |
| 路径 B：不同亮度值个数 | 30 | **179** |
| 路径 B：圆缘过渡剖面 | `51 51 51 51 51 \| 229 \| 255…`（**1** 个中间值） | `51 51 51 51 \| 83 236 \| 255…`（**2** 个中间值，跨两像素） |
| **拾取**：`gc.pick` | `id=7`（命中）/ `0`（空白） | **`id=7` / `0`（逐项相同）** |
| **区域拾取**：`gc.pickRect` | 命中 `1` 个，`id=[7]` | **命中 `1` 个，`id=[7]`（相同）** |

**拾取不受影响**这一条与设计文档 `2026-09-17-jfgl-gpu-picking-design.md:45-60` 的预期一致：
拾取 FBO 是**独立创建的单采样 FBO**（`gl/Framebuffer.java:11-15` 明文写着"恒为单采样"），
与画布的采样数无关。**现在它有实测支撑了。**

### 1.3 证据强度（照实分级）

| 结论 | 强度 |
|---|---|
| `msaa` 参数真的建出多采样 FBO | **实测**（`GL_SAMPLE_BUFFERS=1 / GL_SAMPLES=4`） |
| 多采样结果真的 resolve 到 JavaFX 画面 | **实测**（路径 B：快照里有完整的圆） |
| MSAA 真的让边缘更平滑 | **实测但间接**：过渡带从 1 个中间值变 2 个、不同亮度值 30→179。**但路径 B 的快照是 892×692 逻辑尺寸，对 1113×863 做了重采样**——重采样**自己**会产生中间值。所以 B 是**比较用**的仪器（重采样这个混淆项在两次运行里是同一个常量），**不是绝对量具**。要拿到绝对证据需要按设备缩放出快照（见 §7.2） |
| 拾取不受 `msaa` 影响 | **实测**（`pick` / `pickRect` 逐项相同） |
| `msaa>0` 时画布 FBO 上 `glReadPixels` 非法 | **实测**（`GL_INVALID_OPERATION`，两条路径交叉印证） |
| **`msaa` 不能在运行期改** | **代码事实**：`GLCanvas` 只有 `getMsaa()`、无 setter（jar 的公开签名） |

> ⚠️ **一条尚未实测、但设计依赖它的**：解析式 AA（§4）的**画质**。它没有任何实测支撑——
> §7.1 的第一条就是给它立的闸门。**在跑出像素证据之前，不要在任何地方把它写成"已验证"。**

## 2. 目标与"可配置"的形态

**目标**：让细线、描边、图表系列在斜向/曲面处不再有阶梯状锯齿；且**可配置**。

**"可配置"拆成两个开关，因为它们的时机根本不同**：

| 开关 | 时机 | 住哪 | 为什么必须分开 |
|---|---|---|---|
| `msaa = 0..N` | **构造时** | `FXGLTransfer(msaa=)`，经 DSL 暴露为 `jfgl { antialias { msaa = 4 } }` | 采样数是 FBO 的属性，**`GLCanvas` 没有 setter**（§1.3），运行期改不了 |
| `Gc.antialias: Boolean` | **运行期**，进 `save`/`restore` 状态栈 | `Gc` 的样式栈（与 `fill` / `lineWidth` / `fontSize` / `globalAlpha` 并列） | 解析式 AA 是片元行为，可以**逐次绘制**开关 |

`Gc.antialias` 进状态栈是刻意的：它能表达"只给这一条线开 AA"，
也能 `save` / `antialias = true` / `restore` 做局部开关——与 `lineWidth` 的用法完全同构。

**两个都默认关**（§6）。

## 3. 架构：按"几何知不知道自己的中心线"分工

### 3.1 策略矩阵

| 形状家族 | AA 手段 | 依据 |
|---|---|---|
| **一切描边**：`drawLine` / `strokePolyline` / `strokePath` / `strokeRect` / `strokeCircle` / `strokeEllipse` | **顶点属性 `aDist`** + 片元羽化 | 它们**全都汇进 `StrokeGenerator`**（`strokeRect`/`strokeCircle`/`strokeEllipse` 走的是 `strokeClosedOutline` → `strokeGenerator.stroke`），而生成器**本来就知道**每个顶点离中心线多远 |
| **图表系列**：折线 / 阶梯 / 面积 / 柱状 / 散点 / 频谱 | **顶点着色器多传一个 varying** | 它们的顶点着色器**已经算好了**屏幕空间的线宽与法向（`SeriesShaders` 的 `uHalfWidth` / `aCorner`），只要把"我在带的哪一侧"传下去 |
| **一切填充**：`fillRect` / `fillCircle` / `fillEllipse` / `fillPolygon` / `fillPath` | **MSAA** | 见 §3.2 |
| **文本** | **不动** | SDF 已经在做（`RenderBatch` 的 SDF 片元，`fwidth` + `smoothstep`），它是全仓库唯一一处已有的 AA |

### 3.2 为什么填充交给 MSAA（这是本设计的核心判断）

**判据是"几何知不知道自己的中心线在哪"，不是"解析 vs 非解析"。**

- 描边是**一条带**：`StrokeGenerator` 从中心线向两侧偏移，所以每个顶点到中心线的
  有符号距离是**它自己算出来的**，白送。
- 填充是**一块面**：`Tessellator` 产出**三角形汤**。"内部顶点到边界的距离"**没有定义**——
  耳切出来的内部顶点既不在边界上，也不在任何有意义的位置上。
  要做解析式 AA 就得引入 nanovg 那一路（沿边界铺一圈带距离的 fringe quad，
  或上 stencil / 距离场），**那是另一个量级的工程**。
- 而 **MSAA 恰好擅长填充**：它对多边形边缘的覆盖率是**正确的**，
  它的弱点是**细线**（4 个子样本只有 5 级覆盖，1px 的线分不出更多层次）。

⇒ **两者互补**：MSAA 管宽的、解析式管细的。**用各自擅长的那一半，
而不是强行用一种机制覆盖全部。**

### 3.3 为什么不做 `Material.SDF_SHAPE` 材质

**曾考虑过**：给矩形/圆/椭圆走一个 SDF 片元（一个 quad + UV 带局部坐标），
得到**精确**的 AA 且顶点从几十个降到 4 个。**否掉了**，因为：

- 一个形状一份 uniform（形状类型 + 参数）⇒ **每个形状一条独立 draw call**。
  uniform 不在 `VertexWriter.setState` 的合批判据里，所以相邻的 SDF 形状**合不了批**。
  那是拿"少几十个顶点"换"多几倍 draw call"——而本仓库的实测结论恰好相反
  （`CLAUDE.md`：「**加着色器工作量便宜，加实例数贵**」，瓶颈在**前端**）。
- 要把参数塞进顶点属性才能恢复合批，那要每顶点多 5 个 float（形状类型 + vec4 参数），
  比 `aDist` 的 1 个 float 贵 5 倍，而收益只是解析形状那几种。
- 而**不需要它**：解析形状的**描边**已经自动被 §3.1 第一行覆盖了。

### 3.4 为什么不走 FXAA / 后处理

需要一次全屏 resolve pass（`GLAbstraction` 里**没有** `glBlitFramebuffer`，
也没有多采样纹理/renderbuffer 的任何入口，§1.3 那份签名表可以核对），
而且 FXAA 会**糊掉文字**——本仓库的 SDF 文本是全项目做得最讲究的一处。

### 3.5 为什么 A 必须先行

B（直线线型）要做**虚线**与**圆头/圆角接头**，两者都需要**同一个顶点属性**：

- 虚线要"**沿线弧长**"来算 dash 相位；
- 圆角接头要"到中心线的距离"来判断圆头的外缘；
- 而 **A 要的正是"到中心线的距离"**。

也就是说 **A 定下的那条属性，B 要用两次**。先做 B 再改接缝就是返工两次；
反过来 A 先行只多写一个字段（`aDist` 现在够用，B 再决定要不要加第二个分量，见 §4.4）。

## 4. 接缝一：顶点格式加 `aDist`

### 4.1 布局（24 → 32 字节）与 `aEdge` 的两个分量

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | `vec2 float` | 位置（已烘焙到 NDC） |
| 8 | `vec2 float` | 纹理坐标 |
| 16 | `vec4 ubyte normalized` | 颜色（预乘 alpha） |
| 20 | `uint` | 拾取 ID |
| **24** | **`vec2 float`** | **`aEdge = (横向, 沿向)`** |

**`aEdge.x`（横向）**：到中心线的有符号距离，**归一化到真实半线宽**。
`0` = 中心线，`±1` = 两条真实外缘（`+` 是 `+n` 侧）。归一化的分母是**真实**半线宽，
不是扩展后的。

**`aEdge.y`（沿向）**：到**最近端帽线**的有符号沿路径距离，同样除以真实半线宽。
**`0` 是端帽线，带内为正、带外为负**——片段着色器正是靠这个符号区分"在线内"与"在线外"
（§4.3 那条 `0.5 + y/wa` 要求如此）。

> **★ 2026-09-26 执行期更正：这里原写的是"恒 ≥ 0"，是错的。** 写规格时的疏忽——
> 它同时要求"端帽线是 0"与"几何向外扩 1 像素"，而**扩出去的那圈必然在端帽线之外**，
> 按定义只能是负的。执行者按"向外为负"实现并把这个矛盾提了出来，核过 §4.3 的公式后
> 确认**实现是对的、文档是错的**（公式要 0 在端帽线、带内为正、带外为负）。
> （执行者报告里还指出一个陷阱：`emitCap` 里 `n` 是**向外**方向的左法线，
> 与相邻段四边形的 `n` 反向 ⇒ 端帽的 `±1` 与同侧段四边形的 `±1` **符号相反**。
> 着色器只用 `|横向|`，所以没有后果，但改签名的人要知道。）

- **开放路径**：取该顶点到两端帽的沿路径距离的**较小者**。
- **闭合路径**（无端帽）：取 `(累加弧长 + 全路径长)` ⇒ 恒 ≥ `全路径长/半线宽`，
  **远离 0** ⇒ 那片区域的沿向测试恒为"完全覆盖"，不会在路径起点**凭空造出一条羽化边**。
- **填充与文本**：两个分量都写 `0`。**注意它们与"端帽线"的 0 不冲突**——
  片元靠 `fwidth == 0`（分量在图元上恒定）区分，**不是**靠这个符号。
- **端帽外扩必须做成**显式参数**，不能靠"把折线两端延长一点"来碰运气。**
  ★ **2026-09-26 执行期更正——这里原写着"平头端不需要特判：`alongAt` 的 `min(arc, 全长−arc)`
  在弧长越过全长时自然给出负值"，那句话是错的，而且是可测量为假的。**
  实测（两点线两端各延长 1 局部单位）：沿向只有 `{0.000（两个延长点）, +0.200（真实端点）}`，
  **没有任何负值**。错因很直白：**延长点成了所传折线的弧长端点**，
  `min(arc, 全长 − arc)` 在那里恒为 0；而**任何折线的顶点弧长都不可能超过它自己所在折线的全长**
  ——所以"弧长越过全长"这个条件永远不成立。
  后果（可见）：`y = 0` 的等值线落在**延长后的外缘**，整圈 fringe 都在 ≥ 0.5 一侧
  ⇒ 端帽端边**拿不到羽化**，同时描边**在两端各长出约 1 个设备像素**。
  **正确接法**：`StrokeGenerator.stroke(...)` 收一个 `capExtension`（局部单位，默认 0），
  **非闭合 + `Cap.BUTT` + `capExtension > 0`** 时由它**自己发射**一段外扩四边形：
  真实端线沿向 `0`、外缘沿向 `-capExtension/half`、横向 `±1`。
  于是真实端线 `aa = 0.5`、外缘 `aa = 0.5 − 像素数`（1 像素外正好 0）、
  **描边不变长**（fringe 是透明的）。
  折线**不再被延长**，所以 `alongAt` 的口径不用改。

> **★ 为什么必须有"沿向"** —— 这一条是**写实施计划时才发现的**，初稿只设计了横向一个分量，
> 以为"端帽的 AA 留到 B 再说"。**那个假设是错的**：`Gc.strokeOutline` 硬编码
> `Cap.BUTT`，而平头端的端边**垂直于线段**，它的边界上横向坐标从 `+1` 连续走到 `-1`
> （中途**经过 0**）——也就是说**平头端的边界由"沿向"描述，横向对它一无所知**。
> 只用横向的后果很具体：一条 4px 横线，**上下长边有 AA、左右两端是硬角**。
> 而 B 的虚线相位（弧长）与圆角接头要的也是同一个分量 ⇒ **一次到位比改两次格式划算**。

**开了 AA 时，描边几何要向外扩 1 个设备像素**（`Gc` 用现有的 `matrixScale()`
把"1 设备像素"换算成局部单位）——**两个方向都要**：横向外扩让长边有外侧片元，
**沿向在端帽外扩**让端边有外侧片元。**这一步不是可选的**：
真实边界之外那半个像素必须**有片元**，否则覆盖率永远推不到 0.5 以下（§4.3）。

**`Gc.antialias` 关时**：两个分量一律写 `0`、几何**不扩展** ⇒ 片元走 §4.3 那条
恒 `alpha = 1` 的分支，与现状**逐像素相同**。

`VertexFormat.STRIDE_BYTES` 24 → 32、`WORDS_PER_VERTEX` 6 → 8。

### 4.2 谁写它 —— 成本已实测

| 事实 | 出处 |
|---|---|
| 写顶点的**唯一**出口是 `Gc.emitTriangles` | `Gc.kt` 里 `writer().vertex(` **只有 1 处** |
| `RenderBatch` 里 `.vertex(` / `.quad(` 调用点 | **0 处** |
| `STRIDE_BYTES` / `WORDS_PER_VERTEX` 出现在**3 个**生产文件 | `RenderBatch` / `VertexFormat` / `VertexWriter` |

**因此这次改动比看上去小得多**，具体：

1. `VertexFormat` 加 `OFFSET_EDGE = 24`、改两个常量（+ 受影响的测试）。
2. `VertexWriter` **保留现有 `vertex(...)`**（内部 `aDist = 0`），
   只**新增一个重载** `vertex(..., float aDist)` ⇒ **既有调用点零改动**。
3. `RenderBatch.configureVaoAttributes()` 加第 5 个属性（location 4）。
4. `StrokeGenerator` **并行输出一份 `aDist`**（它内部知道每个顶点是哪一侧的偏移点）。
   它已经有"返回内部数组、不复制"的先例（`rawTriangles()`），照同一种形态加
   `rawEdges()` 即可。
5. `Gc.emitTriangles` 只多一个参数：描边路径传 `strokeGenerator.rawEdges()`，
   其余路径传 `null`（⇒ 全 0）。

**注意 `StrokeGenerator` 的接头**：miter 的尖角顶点**不在**两条外缘上，
它的 `aDist` 应当沿**那条边的法向**取（尖角在外缘的延长线上）。
这一点要在实现时逐接头类型对齐（`BUTT`/`ROUND`/`BEVEL`/`MITER`），
**它正是"接头的 AA 对不对"的判据落点**。

### 4.3 片元怎么用

**不引入任何 uniform**，靠屏幕空间导数自动适配缩放与旋转——与 SDF 文本同一手法。
**两个分量各算一个覆盖率，再相乘**：

```glsl
in  vec2 vEdge;      // (横向, 沿向)
out vec4 fragColor;

// 横向：|x| = 1 是长边的外缘
float wc = fwidth(vEdge.x);
float ac = (wc > 0.0) ? clamp(0.5 - (abs(vEdge.x) - 1.0) / wc, 0.0, 1.0) : 1.0;

// 沿向：y = 0 是端帽线；带内为正。闭合路径与填充的 y 恒远离 0 ⇒ 这一项恒为 1
float wa = fwidth(vEdge.y);
float aa = (wa > 0.0) ? clamp(0.5 + vEdge.y / wa, 0.0, 1.0) : 1.0;

fragColor = vColor * (ac * aa);
```

**`w > 0.0` 这个判别式同时解决了两件事，所以不需要 `uAntialias` uniform**：

1. **填充与文本**（两个分量恒 0）⇒ 该 vary 在整个图元上是常量 ⇒ `fwidth = 0`
   ⇒ 走 `= 1.0`。**天然正确，不是特例。**
2. **`Gc.antialias = false` 的描边**⇒ `Gc` 一律写 0、几何不扩展 ⇒ 同一条路。
   **开关落在 CPU 侧的"写什么"上，而不是片元的 uniform 上** ⇒ 合批不受影响。

**两条覆盖率为什么可以相乘**：横向与沿向是**两条独立的边**。三角形的角上两者都 < 1，
乘积会略微**欠覆盖**（真实覆盖率是 `1-(1-a)(1-b)` 那一类，不是积）；
但角只占一个像素，且 §7.1 的墨量判据会把它量出来。**这是待实测项，不是结论。**

**为什么必须外扩 1 像素**：`clamp(0.5 - d, 0, 1)` 里的 `d` 是**像素中心到边界的像素距离**。
真实边界之外那半个像素若没有片元，覆盖率就永远推不到 0.5 以下——
边缘会从"全亮"直接跳到"没有"，AA 只做了一半（这叫 fringe，nanovg 也是这么处理的）。

**`fwidth` 让这条线与 DPI / 缩放 / 旋转 / 非均匀缩放全部无关**：它量的是**这一次光栅化里**
该 vary 的真实导数，而不是一个预先算好的常量。

> ⚠️ **横向那一条对"细带"会偏厚，正确形式待定——这一点照实记。**
> `abs(vEdge.x)` 取的是"到**最近**那条长边的距离"，于是它**丢掉了"我在带内还是带外"的符号**。
> 带宽接近 1px 时两条长边的覆盖率会互相污染（粗算：1px 的线居中落在像素边界上时，
> 这条公式给两行各 0.75，墨量 1.5px；正确值是各 0.5，墨量 1.0px）。
> 严格形式要把**两条长边的覆盖率相减**，那需要两个"到某条边"的分量而不是一个"到最近边"的。
> **本规格给的是"待实测的目标形态"，不是已验证的结论**（§1.3 已声明解析式 AA 无实测支撑）。
> **§7.1 的墨量判据就是为把它逼出来而设的**：厚度错了，那条会失败。
> 若实测确认细带偏厚，收口路径是**把 `aEdge` 从 `vec2` 扩到 `vec3`**
> （横向拆成"到两条长边各自的距离"），stride 32 → 36。
> **在拿到那条像素证据之前，不要预先按 `vec3` 设计。**

### 4.4 已知代价（照实记）

- **stride 24 → 32**：1M 顶点上限 ⇒ 24MB → **32MB**（`MAX_VERTEX_CAPACITY = 1 << 20`）。
- **`VertexWriter` 的 `flushThresholdVertices` 语义不变**（按顶点数计），
  但每顶点多 8 字节 ⇒ 同一次 flush 的**字节量**增加 1/3。
- **一次格式改动，而不是两次。** 初稿打算先上 `float`（28 字节）、到 B 再扩到 32；
  但 §4.1 那条推导（平头端只靠横向描述不了）把"沿向"变成了 **A 自己的需求**，
  于是直接上 `vec2`。写在这里是为了让将来的人不必重新推一遍
  "为什么 A 需要两个分量"。
- **如果 §4.3 的细带偏厚被实测确认**，格式还要再动一次（`vec2` → `vec3`，36 字节）。
  **那是一条有条件的、未知路径**，不是计划里的一步。

## 5. 接缝二：图表系列的 varying

图表系列**不进 `RenderBatch`**（它们在 `Gc.flush()` 处当场 instanced 绘制，见
`CLAUDE.md` 的「绘制后端」一节），所以 §4 的顶点格式**与它们无关**——
它们要的是**各自顶点着色器里多算一个 varying**。

**不需要新属性**：`SeriesShaders` 的 `aCorner`（单位四边形的四个角，divisor=0）
**已经携带了"我在带的哪一侧"**：

- `LINE_VERTEX`：`aCorner.y ∈ {0,1}` 已被用来选法向的符号
  （`vec2 offset = nrm * halfWidth * (aCorner.y < 0.5 ? -1.0 : 1.0)`）
  ⇒ 只要把它规范化成 `[-1,1]` 并输出为 `vEdge`。
- `STEP_VERTEX` / `AREA_VERTEX` / `BAR_VERTEX`：同理，它们各自已经在用 `aCorner` 定位。
- `SCATTER_VERTEX`：点是**方块** ⇒ 两个轴**各自**携带一个归一化坐标
  （★ 见下：**不能**在顶点上先取 `max`）。

> **★★ 2026-09-26 执行期更正：本节原写"`vEdge` 取两个轴的 `max`（方形 SDF）"——那是错的。**
> **按它写出来一点 AA 都没有**：盒子的四个角上 `max(|2·0−1|, |2·0−1|)` **全都等于 1**
> ⇒ **在顶点上算完再插值出来是一个常量** ⇒ `fwidth = 0` ⇒ 守卫 `(w > 0) ? … : 1.0`
> 直接给出覆盖率 **1**。**着色器编译得过、画得出图、只是没有 AA。**
> **实测证据**：柱状与散点的关/开两帧**逐像素完全相同**。
>
> **错因**：我把**"在顶点上算"**与**"在片元上算"**混为一谈了。
> **距离场必须在片元里由**插值出来的坐标**求**——顶点上先做非线性运算（`max`、`abs` 之后再取极值）
> 再让硬件线性插值，得到的不是那个函数。
>
> **正确形态**：`vEdge` 是 **`vec2`**，片元对两个分量**各自**算覆盖率再**相乘**：
> ```glsl
> vec2 e = abs(vEdge);
> vec2 w = fwidth(vEdge);
> vec2 cov = vec2((w.x > 0.0) ? clamp(0.5 - (e.x - 1.0) / w.x, 0.0, 1.0) : 1.0,
>                 (w.y > 0.0) ? clamp(0.5 - (e.y - 1.0) / w.y, 0.0, 1.0) : 1.0);
> float a = cov.x * cov.y;
> ```
> **单轴图型的第二个分量恒 0** ⇒ 它的 `fwidth` 恒 0 ⇒ 那一轴退化成 1
> ⇒ 乘积就是单轴的覆盖率（**与只算一个轴逐位相同**——折线那四条判据的读数未变即为证）。
> **只对 vary 分量取 `fwidth`**，不要写 `fwidth(表达式)`（那依赖"表达式求导"的实现细节）。

片元与 §4.3 **同一条公式**（`fwidth` + `smoothstep`），只是 vary 换了个名字。

**图表侧的开关键**：`Series.lineWidth()` 之外**不加新字段**——AA 是否生效由
`Gc.antialias` 决定，渲染器把它作为 `uAntialias`（float 0/1）传给片元。
（这里可以用 uniform：系列本来就**一个系列一条 draw call**，不涉及合批。）

## 6. 对既有断言的影响

### 6.1 默认路径逐像素不变

**两个开关都默认关**：

- `msaa` 默认 `GLCanvas.Defaults.MSAA` = **0**（本来就是，不动它）。
- `Gc.antialias` 默认 **false** ⇒ `uAntialias = 0` ⇒ 片元 `a = 1.0` 恒成立。

⇒ 既有 **370 条单测**与**七个校验器**的精确像素期望（如蓝圆角矩形描边 = 3084、±0 容差）
**全部不动**。这是"保护那批断言"的必要条件，也是它们花了整轮才立住的代价换来的。

⚠️ **但"像素期望不动"不等于"测试一行不改"**：`VertexFormatTest` / `VertexWriterTest`
里与 `STRIDE_BYTES` / `WORDS_PER_VERTEX` / 缓冲区大小有关的断言**必须跟着改**
（那是**格式**的断言，不是**画面**的断言——两者别混）。这是一次**预期内**的改动，
不是回归。

### 6.2 打开之后会动什么（必须提前说清）

- **`Gc.antialias = true`**：描边**边缘**的半透明像素增加 ⇒ `PipelineVerifier` /
  `PathVerifier` 那一批**绝对像素数**会移动。**这是真实的改变，不假装它能不变。**
- **`msaa > 0`**：**★ 六个**校验器立刻失去读数能力**（`glReadPixels` 非法，§1.2）。
  ★ **2026-09-26 执行期更正**：这里原写"**全部七个**"，是**过度概括**——
  `FftVerifier` 读的是 **SSBO**（`glGetBufferSubData`）**不是画布 FBO**，所以**不受影响**：
  实测（短路守卫 + `msaa=4`）**50 条全过、输出与 `msaa=0` 逐行相同**。
  ⇒ 真正失去读数能力的是 `Pipeline` / `Path` / `Pick` / `Click` / `Text` / `Chart` **六个**。
  **守卫仍然挂在七个上**（`FftVerifier` 那条是**纪律、不是实测的必要性**，
  它的注释照实写明了这一点）——**"统一挂"与"必要性相同"是两件事**。
  它们会读回全 0 并**响亮失败**（不是静默通过）——但那失败信息会像是"画面全黑了"，
  **必须在 `FXGLTransfer` 或校验器入口加一条守卫**：`msaa > 0` 时**明确拒绝**
  像素回读并打印原因（"多采样画布上 `glReadPixels` 非法，请用 msaa=0 跑像素校验"）。
  这条守卫本身要有断言钉着（§7.3）。

## 7. 验证策略

### 7.1 解析式 AA 的像素判据

**复用 `TextVerifier` 的思路**（那是全仓库唯一一条已经证明有效的 AA 断言）：
**量边缘过渡带，而不是量像素总数**。

同一帧里画两份**同一条几何**（一份 `antialias = true`、一份 `false`），逐项对照：

| # | 断言 | 判据 | 它挡的是什么 |
|---|---|---|---|
| ① | AA **关**时确实没有中间值 | 该线周围既非背景也非线色的像素数 **= 0**（精确） | 对照组本身被污染 |
| ② | AA **开**时过渡带存在 | 该像素数 **= `4W`**（W = 窗宽列数；**精确**，出处见下） | `aDist` 没被写进去（恒 0）⇒ ② 直接为 0 |
| ③ | **线心没移位、没变淡** | **中心线那一带**（45° 下是 `\|m\| ≤ 1` 那三条对角带）上的纯色像素数两种模式**精确相等** | 整体平移、整体降透明度 |
| ④ | **墨量守恒** | **对"真实面积"断言**（精确），**不是**对 AA 关的对照组 | 变粗 / 变细 / 细带偏厚（§4.3 那条待定公式） |

> **★★ 2026-09-26 执行期更正：② 与 ④ 我原来都写错了，被实测推翻。**
>
> **② 原写"`> 0` 且 `≤ 线长 × 2`"——那个界隐含"每列 2 个过渡像素"，那是**轴对齐**线的情形。**
> 45° 下实测是**恰好 `4W`**（每列 4 个：`m = ±2` 与 `±3` 各两个）。
> 原界按字面只有 `2W` ⇒ **一条正确的实现会被它判为失败**。已改成精确值。
>
> **④ 原写"墨量守恒 = `aaOnInk == aaOffInk`"——那是一条**恒假断言**，而且它本来就不该成立。**
> 实测 **115400 对 102000，差 11.6%**。原因是**硬边的本性**：
> 45° 直线走**像素中心采样**，只有 `|m| ≤ 2` 的像素中心落在真实带内
> ⇒ 有效宽度 `2√2 ≈ 2.83` 而不是 4（**阶梯内接**于斜带，系统性偏细）；
> 而覆盖率斜坡是**面积守恒**的。⇒ **参照系必须是"真实面积"，不是对照组。**
> 解析值出处：`Σ_{|m|≤3} cov(m) = 1 + 2·1 + 2(√2−0.5) + 2(√2−1) = 4√2`，
> 与窗内真实面积**逐项相等**（实测 `115400` 对解析 `115399.8`，**相差 +0.2**）。
> **★ 窗形状是关键**：每一列必须**完整包住横截面**；方形窗会**少掉** `O(1)`（★ 见下）
> （`4√2·S−8.14` vs `4√2·S−8`），**精确相等就没了**。
> 那个 `+0.2` 来自 8 位取整边界：**`|m| = 3` 读 136 而非 135**
> （解析 `135.4996`，被推过界 +0.5；而 `|m| = 2` 解析 `237.4996` 是**向下**取整、**没被推过界**，
> 校验器自己印的 `#EDEDED×200` 就是 237）。
> 界取 `±2W` 是**必需项而非余量**——两个羽化等级的解析值落在取整边界**外 0.0004**，
> 本机浮点噪声就推过去了。**但它仍窄到能分辨真缺陷**（见 §7.5 的变异读数）。
>
> ⚠️ **这里原先把档位写成了 `|m| = 2` 读 238——那是错的，而且是"抄来的"。**
> 实现者报告里的这句我**没核实就转述**进了规格与计划，而它与校验器**自己打印的直方图相反**。
> 这是本次执行里**第三次**同类动作（前两次：Task 2 的"13.0"、Task 3 的"8 设备像素"）。
> 三次都不是算错，是**把别人报告里的事实当既成事实转述**。

**③ 为什么只取线心、不取"总纯色数"**：开了 AA 之后，最外侧那一圈**纯色**像素
本来就会变成过渡像素，总纯色数**必然略减**。写成"总纯色数相等"会是一条
**恒假断言**——那种断言在本仓库比没有断言更坏。而中心线那一行离边缘足够远，
两种模式下都是满覆盖，**它相等是成立的**。

**④ 墨量守恒的形式**：`墨量 = Σ (luma − 背景luma)`，对窗内逐像素求和。
- **参照系是"真实面积"**（`窗内真实面积 × 亮度差`），**不是 AA 关的对照组**——理由见上。
  用 45°、线宽 4px 的线；解析值 `4√2`（出处见上），**断言精确相等**（实测相差 +0.2）。
  界取 `±2W`，那是**取整边界所需的最小值**，不是随手留的余量。
- **对照组（AA 关）照样要读，但它是一条**独立的读数**，不是 ④ 的期望值**：
  实测 `5W × 204 = 102000`（**精确**）。它证明的是"硬边把斜带的面积系统性少算了 11.6%"，
  而那正是 AA 存在的理由之一。
- **另用 1px 的线只断言方向**：`墨量(AA)` 落在 `墨量(关) × [0.9, 1.1]` 内。
  留 10% 是因为 §4.3 那条细带公式**已知可能偏厚**（**待实测项**）；
  **这条一旦失败，说明该换成双分量 `aDist`**（§4.3 末尾那条收口路径），
  而不是"把容差放宽"。

> **★ 实测更新（2026-09-26）：1px 那条容差当前**没有兜住任何东西**。**
> 四种组合（线宽 1、两种相位 `.25` / `.50`、AA 开/关）实测**墨量完全相等**
> （都是 `81600`，即 **1.000 px/列**，比值 **1.0000**）⇒
> **§4.3 那条"细带可能偏厚"的担心不成立**（它是**错误归一化**的产物）。
> 容差留着（它标注的是"要暴露什么"），但**别把它当成"已知有偏差"的证据**。
>
> ⚠️ **那条 10% 是"待实测项"的容差，不是"期望值"**——两者性质不同，别混。
> 本仓库反对的是**用容差藏住真缺陷**（蓝描边那条 5% 藏了 MITER 漏半块）；
> 这里 10% 是**明确标注了它要暴露什么**的容差，且判据的主力是那条精确断言。

**反向断言（防橡皮图章）**：把 `aDist` 写成常量 `0` ⇒ ① **必须**通过
（退化成硬边）而 ② **必须**失败。这一对保证判据不是恒真的。
若 ① 也失败，说明对照组本身有问题，那比 ② 失败更值得先查。

### 7.2 MSAA 的判据

**不能用 `glReadPixels`**（§1.2）。用探针里那条**路径 B**（JavaFX 快照），
并且**要修掉它的混淆项**：快照必须按**设备缩放**取（`SnapshotParameters` 里给
`Scale` = `bridge.deviceScale(node)` 的倒数关系），否则快照自带重采样，
"中间值"分不清是 MSAA 的还是重采样的。

判据与 §7.1 **同构**（① 对照组无中间值 / ② 实验组有过渡带 / ③ 线心相等 / ④ 墨量守恒）。
**同样不要把 ③ 写成"总像素数相等"**——那在 MSAA 下也是恒假的（AA 会把最外圈像素
从"纯色"变成"过渡色"）。

### 7.3 配置项本身的判据

- `Gc.antialias` 进 `save`/`restore` 栈 ⇒ 单测（`Gc` 的状态栈是纯内存的，
  构造 `Gc` 只需要一个 `RenderBatch`，而它能用 `FakeGLAbstraction` 建起来 ⇒ **零 GL 上下文**）。
- `msaa > 0` 时校验器的**拒绝守卫** ⇒ 一个开窗探针断言它**明确报错**，
  而不是读回全 0 后当成"画面全黑"去报一堆假失败。

### 7.4 `StrokeGenerator` 那一半可以单测

`aEdge` 的输出是**纯算术**（与 `rawTriangles()` 同族），最适合单测——
**这是本子项目里唯一能脱离 GL 验证的那一半**：

- **横向**：一条水平直线段的四个角，`aEdge.x` 恰好是 `-1, -1, +1, +1`
  （`+n` 侧是 `+1`）。
- **沿向（开放）**：靠近起点端帽的顶点 `aEdge.y` 小、靠近终点的从**另一头**起算
  ⇒ 中段取到最大值；两端帽那一排恰好是 `0`。
- **沿向（闭合）**：**没有任何**顶点的 `aEdge.y` 接近 0
  （这正是"闭合路径不要凭空造羽化边"那条判据；实现用的是
  "累加弧长 + 全路径长"）。
- **接头**：MITER 的尖角顶点落在**外侧边界**上，它的 `aEdge.x` 应与同侧的偏移点**同号**，
  中心的关节顶点是 `0`。
- **退化输入**（零长段、重复顶点、`count < 2`）不产生 `NaN` —— 与 `StrokeGenerator`
  既有的"所有输出顶点都是有限值"承诺一致。

### 7.5 变异验证（每条都必须让**定向的**断言倒下）

| 变异 | 预期倒下的断言 |
|---|---|
| `aEdge` 两个分量恒写 `0` | ②（AA 开的过渡带为 0）+ §7.4 的横向断言；**① 必须照常通过** |
| 横向的符号写反 | ④（墨量守恒——线会整体内缩一档）+ §7.4 的符号断言 |
| 片元里 `abs(vEdge.x)` 写成 `vEdge.x` | ②（只剩一侧长边有过渡） |
| 沿向的起点算成"到**远端**端帽的距离" | §7.4 的沿向断言 + ②（一端帽硬边） |
| 闭合路径的沿向不加"全路径长" | §7.4 的闭合断言 + ②（路径起点凭空多一条羽化边） |
| `clamp(0.5 - …, 0, 1)` 的 `0.5` 改成 `0.0` 或 `1.0` | ④（墨量整体变一倍或归零） |
| 描边几何**不扩那 1 像素** | ② 仍在、但 ④ 失败（边界推不到 0.5 以下 ⇒ 边缘偏厚） |
| 把两个 `w > 0.0` 判别式删掉（直接用 `fwidth` 做除数） | 填充路径出 `NaN` ⇒ 大片像素变黑，①③④ 全倒 |

**后三条是这一组里最有价值的**——它们分别钉住 §4.3 里那三处"不做就静默画错"的地方
（fringe 扩展、除零判别、闭合路径的沿向原点），而这正是本仓库历史上的缺陷形态。

### 7.6 探针的去留

`MsaaProbe.kt` 现在是**临时探针**（本仓库的元规则：探针用完要删）。
它的两条读数路径有**长期价值**（§7.2 要用），建议**改造成 `MsaaVerifier`** 而不是删掉
——但那是计划里的一步，不是本规格的结论。**在它变成有断言的校验器之前，
它不构成任何"已验证"的依据。**

## 8. 明确不做的

| 不做 | 理由 |
|---|---|
| 多边形/任意路径**填充**的解析式 AA | §3.2。三角形汤里没有中心线；要做就要 nanovg 那一路，是另一个量级 |
| `Material.SDF_SHAPE` | §3.3。每形状一条 draw call，换来的只是少几十个顶点，方向反了 |
| FXAA / 任何后处理 | §3.4。需要 resolve pass（`GLAbstraction` 没有 blit），且会糊掉 SDF 文本 |
| `GL_LINE_SMOOTH` / `GL_POLYGON_SMOOTH` | 驱动相关、质量差，且与预乘 alpha 混用有已知暗边问题；我们的几何全是三角形，线图元根本不参与 |
| `GL_SAMPLE_ALPHA_TO_COVERAGE` | 它把 alpha 当覆盖率，而本仓库的 alpha 有别的语义（`globalAlpha`、半透明描边），混用会让半透明图元的边缘**变薄** |
| 运行期切换 `msaa` | 不可能（§1.3，`GLCanvas` 无 setter）。DSL 里若有人试，应当**明确报错**而不是静默忽略 |

## 9. 分阶段（给实施计划的输入）

1. **顶点格式 + `aEdge`**（`VertexFormat` / `VertexWriter` / `RenderBatch` 属性 / 测试）。
   此时一切行为不变（两个分量全写 0）。
2. **`StrokeGenerator` 输出 `aEdge`**（纯计算 + 单测，§7.4）。行为仍不变
   （还没人读它）。
3. **描边片元羽化 + `Gc.antialias` 进状态栈 + 几何外扩 1 像素**（§4.1 / §4.3）。
4. **`PipelineVerifier` 的 AA 变体**（§7.1 那四条 + 反向断言 + §7.5 的变异）。
5. **图表系列的 `vEdge` + `uAntialias`**，以及 `ChartVerifier` 的 AA 变体。
6. **MSAA 配置项**（DSL 暴露 + §6.2 那条拒绝守卫 + §7.2 的判据）。
7. 文档：`CLAUDE.md` 的顶点格式那一行（24 → 32）、以及"MSAA 与像素校验器互斥"这条。

> **顺序是有依赖的**：1 → 2 → 3 → 4 是硬序（前三步每一步都能单独验证且**行为不变**，
> 第四步才第一次改变画面）。5 与 3 共用片元公式但互不阻塞，6 完全独立。
> **3 完成之前不要动 5**——两边会把"片元公式长什么样"各写一份。
> **第 4 步是把 §4.3 那条"细带可能偏厚"逼出结论的地方**：它若失败，
> 收口是把 `aEdge` 扩到 `vec3`（§4.3 末尾），那要回头改第 1 步的布局。
