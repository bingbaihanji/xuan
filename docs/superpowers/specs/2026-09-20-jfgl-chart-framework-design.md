## 0. 这份规格只覆盖三块中的第一块

用户的需求里有三块**互相独立、可以分别交付**的东西，且依赖方向清楚：

| | 内容 | 判据 | 规格 |
|---|---|---|---|
| **① 图表类框架** | 数据容器、轴与刻度、脏区间、颜色 LUT、图表装配。**纯计算，零 GL 依赖** | 能否脱离 GL 上下文单测 | **本文档** |
| **② GPU 绘制后端** | 把 ① 的产物变成 GL 顶点与 draw call：波形、散点、柱、热力图、瀑布 | 需要 GL 上下文 | 另出 |
| **③ GPU 计算** | 在画之前先算：FFT、降采样、包络、密度累积（数字荧光） | 需要 GL 上下文 | 另出 |

**划这条线的判据是「能不能脱离 GL 上下文跑测试」**，不是"看起来像哪一层"。这样 ① 可以被完整单测——而单测是这个项目唯一能对纯计算做的事。

**交付顺序**：① → ② → ③。① 的接口必须为 ②③ 留好位置（尤其"脏区间"与"GPU 常驻"这两件事要在一开始就在接口里，不能后补）。

## 1. 目标

面向**示波器这类实时高吞吐场景**（数据持续高速涌入、要求实时计算与显示）的图表框架，同时能承载静态科学绘图（几十万点的曲线、热力图）。

**第一优先级是实时路径**，静态路径同架构支持但排在后面。

**立项理由就是高性能**：底层直接用 GPU 绘制与计算，而不是像 JavaFX Canvas 那样逐像素 CPU 光栅化。

## 2. 非目标（本规格明确不做）

写在这里是为了让后来者知道"这是刻意不做，不是漏了"。

| 不做 | 理由 |
|------|------|
| 任何 GL 调用 | 那是 ②③ 的事；① 出现 `gl*` 就是分界线画错了 |
| 对数轴以外的非线性轴 | 本期只有 `LINEAR` / `LOGARITHMIC` / `TIME` / `TEXT` |
| 3D | 2D 管线的顶点格式没有 z |
| 动画补间 | GPU 化的增益动画应该是一个 uniform 进度值，不是 N 个 `KeyValue`（fxcharts 的 `Timeline` 是反面教材） |
| 富文本标注 | 子项目 B 的文本只有单行 |
| 数据持久化 / 导入导出 | 与应用有关，不属于框架 |
| 多写者数据源 | 见 §5.4——**这是硬前提，不成立则整个无锁设计要换** |

## 3. 前置事实（已实测，不要重新猜）

**3.1 实际 GL 上下文是 4.6，不是 3.3。**
用开窗探针实测（`GL_VERSION = 4.6.0 NVIDIA 581.29`，RTX 3060 Laptop，`MAJOR.MINOR = 4.6`），并**实际编译 + 链接 + dispatch 了一个最小 compute shader**（SSBO 写入，输入 1..8 输出 2..16，端到端验证）。
即：计算着色器、SSBO、`imageStore`、shared memory 原子操作**全部可用**。项目里那 5 个 `#version 330 core` 着色器能跑是因为 4.6 向后兼容，**不是因为上下文是 3.3**。
> 这条要同步修进 `CLAUDE.md`——它现在暗示管线是 GL 3.3，会让人误以为 compute 不可用。

**3.2 仓库里已有 `gpu/GPUFFT.java`（`#version 430`，Cooley-Tukey radix-2 + SSBO），但没有任何人引用它。** 它现在就是可用的，③ 可以直接复用或重写。

**3.3 参考项目的结论（都读代码核实过）：**

- **chart-fx**：`chartfx-dataset` 模块对 JavaFX **零依赖**，`DataSet` 接口很窄。**没有任何 GPU**，全走 `GraphicsContext`。它的热路径设计（可复用缓冲 + 原地缩减 + 二分查可见窗口 + 零分配）是最该抄的部分——**这是它能跑实时的真正原因**。
- **fxcharts 不是用户的项目**，是 `HanSolo/charts`（Gerrit Grunwald）的未改动上游克隆，本地只改了构建配置。**读不出用户的设计偏好**，只能读它的图表类型清单。它**零性能设计**（`XYSeries.getMinX()` 每次调用全量流式扫描、热力图逐像素 `new Color`、刻度用 `BigDecimal`），且**眼图与甘特图完全不存在**。
- **scope（Qt 示波器）**：**GPU FFT 是死代码**——`QOpenGLContext::currentContext()` 恒空（两个调用方都在数据到达时触发，那时没有 GL 上下文；整个 `src/` 里 `makeCurrent()` 只出现在 4 个 widget 的析构函数里），所以每帧实际走 CPU。**这正是 JFGL 的 CLAUDE.md 已经钉死的规则**（GL 调用必须在 `onRender` 内）。它的**数字荧光密度光栅化**（`rasterize.comp`：每像素列一个 workgroup、shared memory 内做列直方图 + `atomicAdd`、一行 `alpha + persistScale` 就是余晖衰减）与**瀑布图的双倍宽环形纹理 + 墙钟锚定亚像素滚动**是 ②③ 最值得拿的东西。

## 5. 数据模型

### 5.1 为什么接口要带"脏区间"

`chart-fx` 的 `DataSet` 是**随机访问**的（`get(dim, index)` + `getDataCount()`），这对静态数据天经地义。但示波器要的是**追加**。

**问题不在"怎么读数据"，而在"渲染器怎么知道哪些数据是新的"。**

`chart-fx` 有脏位，但那是**图表级的一个全局标志**——所以它的渲染器每帧仍要把 8 个步骤全走一遍（二分查窗口、重烘屏幕坐标、重做缩减）。**脏位只说明"要重画"，没说明"重画哪一段"。**

而 ② 要的是 **GPU 常驻 + 增量上传**：数据上传一次长期驻留，只有新增的那几十个点走 `glBufferSubData`。**这要求接口把"脏区间"作为一等公民。**

### 5.2 接口

```java
public interface ChartData {
    /** 各维度自己声明范围与名称单位——轴只是显示窗口，不去遍历数据。 */
    AxisRange axisRange(int dim);

    /** 当前的数据项数。 */
    int itemCount();

    /** 随机访问仍在：静态数据靠它，流式数据的可见窗口也靠它。 */
    double value(int dim, int index);

    /** 每次内容变更递增。渲染器靠它判断"要不要重新上传"。 */
    long revision();

    /**
     * 自 {@code sinceRevision} 以来哪一段变了。
     * 返回 [firstDirty, lastDirty) 半开区间；无变化时返回空。
     */
    DirtyRange dirtyRange(long sinceRevision);
}
```

**为什么是这个形状**：

- `axisRange` 在数据侧（抄 chart-fx）：避免了"轴去遍历全部数据"的耦合，也让一个范围能被多个轴共享。多 Y 轴因此是**自然结果而非特例**。
- `revision` + `dirtyRange` 是 ① 相对 chart-fx 的**唯一实质增强**，也是高性能这条路能不能走通的关键。
- 静态实现（`ArrayChartData`）在 `revision` 不变时直接报"无脏区"，渲染器一次上传后**永不重传**。流式实现只报"新加了 N 个"。

### 5.3 两个实现

**`ArrayChartData`**：一次性数据，`revision` 只在整体替换时递增。**这是静态科学绘图的路径。**

**`RingChartData`**：SPSC 环形缓冲，采集线程写、GL 线程读。见 §5.4–5.6。

### 5.4 并发模型：单生产者单消费者（硬前提）

```
采集线程（唯一写者）                GL 线程（唯一读者）
  写 data[w & (cap-1)]               读 writeIndex（volatile，acquire）
  ↓                                     取 [readIndex, writeIndex) 这段
  写 writeIndex++（volatile，release）  上传顶点
                                      readIndex = writeIndex
```

**不用锁**：采集线程是实时的，**它一次都不该被 GL 线程阻塞**。

> **硬前提：只有一个写者。** 采集线程由使用方自己起（已确认），所以这个前提成立。
> **若将来数据源改成网络/串口回调**（回调线程可能是 IO 线程池里的任意一个），**单生产者前提就不成立，整个无锁设计必须换掉**（多写者需要 CAS 或加锁）。这条写在类文档最前面。

### 5.5 三处正确性要点（每一条错了都不报错）

1. **先写数据、再递增索引。** `volatile` 写在 Java 里有 release 语义、读有 acquire 语义，这个顺序保证读者看到索引时数据一定已可见。**反过来写就是经典的半初始化读取**——读者拿到索引、读到的却是还没写完的数据。
2. **索引用 `long` 不用 `int`。** 每秒几百万点，`int` 几十分钟就溢出。**溢出后静默回绕，全盘错乱**——而且是在运行了很久之后才发生，最难查。`long` 在 2^63 处才溢出，实际不可达。
3. **容量取 2 的幂，用 `& (cap - 1)` 取模。** 不是为了快，是为了**避免负索引**：Java 的 `%` 对负数返回负值，`w % cap` 在 `w` 为负时直接读到错的位置。

### 5.6 溢出：丢弃 + 缺口标记 + 计数

采集线程比 GL 线程快是常态（掉帧、窗口被遮挡），**写者绕过读者一定会发生**。

**策略：丢弃最旧的数据，并且必须让它可见。**

- 维护 `lostSamples()` 计数，暴露给 UI。**"这一屏数据完整吗"本来就是示波器用户要问的问题。**
- **必须在丢弃处插一个缺口标记（gap marker），让渲染器据此断开折线。**

> **缺口不能连过去。** 不插标记的话，波形会拉一条直线穿过缺口——**那条直线是假的，它显示了一个不存在的信号**。
> 这比不显示更糟，而且看起来完全正常。这是本项目最典型的"静默错误输出"，只是这次藏在数据层。**渲染器侧必须有一条断言钉住它。**

**为什么不阻塞采集线程**：宁可丢点，不可丢时间。在采集卡场景下"阻塞"往往意味着硬件 FIFO 溢出，**丢得更多**。
**为什么不让它无限增长**：采集是持续的，内存最终会爆；而"爆"的时候离出问题的地方很远，**把立即的、可观测的问题换成了延迟的、不可观测的**——是最糟的一种。

**缺口怎么表示（钉死，不留两种解法）**：**缺口位置上的 `value()` 返回 `NaN`**，不额外加 `isGap(index)` 方法。

理由是它与 §10 那条"数据里有 NaN → 断开折线"**天然合一**：渲染器只需要一条规则（"遇到 NaN 就断开"），不必知道也不该知道"这个 NaN 是采集丢包还是传感器本身吐的"。多一条 `isGap` 会让渲染器有两个判断点，而它们迟早会不一致。

## 6. 轴与刻度

**数据声明范围，轴是"显示窗口 + 换算器"。** 这条抄 chart-fx：`Axis` 不持有数据，只持有 `AxisRange` 与当前显示窗口。

- `AxisType`：`LINEAR` / `LOGARITHMIC` / `TIME` / `TEXT`
- 三级刻度（主/中/次）+ nice number 选步长
- **用 `double` 算术，不用 `BigDecimal`**（fxcharts 的 `Axis.java:1399` 用 `BigDecimal` 算刻度，高刷新率下会成为热点，而且没必要）

`dataToDisplay(value)` / `displayToData(px)` 一对互逆映射，是轴的全部职责。

**这一块是纯算术，零 GL 依赖**，是本规格里最适合写单测的部分之一。

## 7. 颜色：`ColorMapping` → 1×256 LUT

`ColorMapping` 持有一组 `Stop[]`（科学配色，如 `INFRARED_4`、`CMRMAP`），能生成一张 **1×256 的 LUT**（`byte[1024]`，RGBA）。

**这正好落在 JFGL 已定的"所有 Paint 归一化为纹理"上**：热力图换配色从 fxcharts 的"整幅逐像素重算"变成"换一张纹理"。**这是收益最大的一条。**

LUT 生成是纯计算，可单测（断言端点颜色、单调性、无越界）。

## 8. 滚动是 uniform，不是重建

**顶点缓冲也应该是环。** 这条现在定比后面改便宜。

示波器的窗口是**滚动**的。按常规做法"每帧重建可见窗口的顶点"，窗口滑动一格 → **所有点的 x 坐标都变了** → 整个顶点集每帧全量重传——**增量上传的好处全部抵消**。

正确做法：

```
数据环：采集线程持续追加
顶点环：GL 线程把新点追加到顶点环的对应槽位（只上传新增的那几十个）
        uniform uScrollOffset 表示窗口相对顶点环的偏移
着色器：gl_Position.x -= uScrollOffset
```

**每帧只上传新增的点，滚动完全免费。**

这与 scope 瀑布图那个"双倍宽环形纹理 + 墙钟锚定亚像素滚动"是同一个思路的两种应用——**它的滚动永不出现接缝，也是靠这个**。

> 注：本节的实现落在 ②，但**接口承诺在 ①**——`SeriesRenderer` 的签名必须允许"只给我脏区间，其余你自己留着"。

## 9. 渲染器边界：纯函数，不是场景图节点

```java
public interface SeriesRenderer {
    /** 数据 + 轴 → 顶点。自己不持有数据，也不认识场景图。 */
    void render(RenderContext ctx, ChartData data, Series series, Axis[] axes);
}
```

**这是 ① 与 ② 的接缝。** 注意 `RenderContext` **不属于 ①**——它是 ② 提供的"给你一支笔"的上下文（顶点写入器、当前帧号、纹理槽位等）。① 只声明签名，② 给它血肉。这样 ① 保持零 GL 依赖，而 ② 可以自由决定上下文里放什么。

**避开 chart-fx 的坑**：它的 `Renderer` 接口混了三件事（`render()` 绘制、`updateAxisRange()` 数据域、`getNode()`/`drawLegendSymbol()` 场景图），而且 `AbstractRenderer extends Parent`——**渲染器本身是场景图节点**，逻辑与节点树耦合。

JFGL 里 **`SeriesRenderer` 是纯函数**：数据 + 轴 → 顶点。**轴、网格、图例各自独立，都不是场景图节点。**

**图型是属性组合而非类层级**（抄 chart-fx）：`ErrorStyle × LineStyle × 布尔量`，一个 switch 覆盖大部分 2D 图型，**零新类出很多图型**。

## 10. 错误处理

| 情况 | 行为 |
|------|------|
| 数据出现缺口（溢出丢弃） | 插缺口标记，渲染器断开折线；`lostSamples()` 可查 |
| 数据里有 NaN / Inf | **不静默跳过**——跳过会让折线连过去，又是一个假信号。渲染器应断开折线，与缺口同等对待 |
| 轴范围退化（min == max） | 自动扩成一个最小可视跨度，不除零 |
| 对数轴上出现 ≤ 0 的值 | 明确处理（跳过或钳到下限），**不产生 NaN** |
| 容量不是 2 的幂 | 构造时抛 `IllegalArgumentException`（避免 §5.5 第 3 条的负索引） |

## 11. 测试策略

沿用本项目纪律：**纯计算的写单测，需要 GL 的写像素校验器，两者都要变异验证。**

**单测（本规格的全部内容都可测）：**

| 测试类 | 覆盖 |
|--------|------|
| `TickGeneratorTest` | nice number 步长、三级刻度的包含关系、退化范围、对数与时间轴的标签 |
| `AxisTest` | `dataToDisplay` / `displayToData` 互逆、边界、退化范围不除零 |
| `RingChartDataTest` | 写入/读取索引推进、**环绕**、溢出丢弃、**缺口标记出现在正确位置**、`lostSamples` 计数、`revision` 递增、容量非 2 的幂抛异常 |
| `ColorMappingTest` | LUT 端点颜色、单调性、越界输入钳位 |
| `ArrayChartDataTest` | 静态路径 `revision` 不变时报无脏区 |
| `ChartDataConcurrencyTest` | **冒烟测试**：单写单读跑一段时间，断言无撕裂/无索引回退。**如实标注强度——正确实现永远通过，但不保证抓得住错误实现**（本项目已有教训） |

**变异验证**：每条断言都要能指出"把哪一行改错会让它失败"。本规格里最容易写成橡皮图章的几处：
- 缺口标记：变异成"不插标记"→ 断言必须失败（否则那条断言是恒真的）
- 索引 `long` → `int`：**变异后短期内不会失败**，要跑足够多轮才能暴露——如实记录
- 环绕：变异成"不取模"→ 越界

## 12. 已知风险

**R1：并发测试的强度有限。** `ChartDataConcurrencyTest` 是冒烟探测器，**不是保证**。真正的正确性来自 §5.5 那三条被写死的不变式 + 代码评审。

**R2：`dirtyRange` 的语义在"窗口滑动"时会变复杂。** 环形缓冲滚动时，脏的不只是"新点"，还有"滑出窗口的旧点"。本规格把这点留给 `RingChartData` 的 `dirtyRange` 实现，**实现时要在类文档里写清"哪些情况算脏"**，并针对每一种写测试。

**R3：`ChartType` 用属性组合会随图型增多而膨胀。** chart-fx 用 `ErrorStyle × LineStyle × 布尔量` 覆盖了大部分 2D 图型，但热力图/眼图这类**不是属性组合能表达的**，会是独立的渲染器。这是可接受的：**属性组合管"同一套顶点怎么画"，独立渲染器管"顶点怎么来"。**
