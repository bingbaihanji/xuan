## 3. 前置事实（**全部实测**，不要重新猜）

### 3.1 GL 上下文是 4.6 compatibility，compute 与 SSBO 可用

`GL_VERSION = 4.6.0 NVIDIA 581.29`，`GL_CONTEXT_PROFILE_MASK = 2`（compatibility）。
已用开窗探针**实际编译 + 链接 + dispatch** 过一个最小 compute shader（`#version 430`、
SSBO 写入、输入 `1..8` 输出 `2..16`，回读恰好两倍）。

### 3.2 `gl/` 里**没有任何** SSBO 抽象

SSBO 只以裸 LWJGL 调用存在于 `gpu/GPUFFT.java` 里。`GLAbstraction` 的 SSBO 相关方法数是 **0**。

### 3.3 ⚠️ `gpu/GPUFFT.java` **不能用**——三层缺陷（`GpuFftVerifier` 实测，提交 `adab313`）

| | 缺陷 | 后果 |
|---|---|---|
| ① | `uint half = 1u << u_stage;` —— **`half` 是 GLSL 保留字** | 默认着色器**编译不过**，`new GPUFFT()` 直接抛 `RuntimeException`。**它从未成功运行过一次** |
| ② | 三个 uniform 声明成 `uniform uint`，而 `dispatchFFT` 用 `glUniform1i` 赋值 | `GL_INVALID_OPERATION` **且值不生效** → `u_N` 恒为 0 → 每次提前返回 → **输出逐位等于输入** |
| ③ | DIT 蝶形要求输入先位反转，而那 6 行算出的 `rev` **从头到尾没被引用** | 输出等于 `DFT(输入按位反转)`，**峰值落在错误的 bin 上** |

③ 的指纹：与 `DFT(x∘ρ)` 的误差 **`5.96e-08`**（float32 精度极限），与真 DFT 的误差 **`0.998`**。
反证：只在 CPU 侧先把输入位反转再上传，三个频率的峰值**立刻回到正确位置**。

**本规格要避开这三条线**——它们是这份设计的直接输入。

### 3.4 参考项目 ngscopeclient（`D:\Programming\CProjects\scopehal-apps`）的调研结论

**它是 Vulkan + VkFFT，API 层面没有可搬的东西**；可搬的是参数与产品决策：

| 项 | 它的做法 |
|---|---|
| 窗函数 | 4 选 1；`Spectrogram` 默认 **Blackman-Harris** |
| **窗增益补偿** | **Hamming ×1.862、Hann ×2.013、BH ×2.805、矩形 ×1**——换窗**不改变幅度读数** |
| 纵轴 | **50 Ω 上的 dBm**（`10*log10(功率)+30`），默认视图 **0 dBm 顶 / −70 底** |
| 显示抽稀 | **取 max，不取平均**（注释写明 `keeps peaks from fading away as we zoom out`） |

**它自己有一个 bug，而它的单元测试抓不到**：BH 窗第三项写成 `cos(6*num)`（`num = 2πi/N`），
实际是 `cos(12πi/N)`，教科书应为 `cos(3*num)`——**而测试的黄金模型照抄了同一个公式**。
**断言与实现犯同一个错，"测试通过"因此什么都没证明。**（见 §10 R4）

## 4. 架构

### 4.1 三块，依赖方向清楚

```
gl/            SSBO 抽象（新）                        不依赖任何上层
   ↑
gpu/           FFT 计算核（新）                        依赖 gl/
   ↑
chartrender/   频谱渲染器（新）                        依赖 gpu/ + chart/ + gl/
chart/         ChartType 加一个常量 SPECTRUM          ← 唯一的改动，见 §4.4
```

### 4.2 SSBO 抽象（`gl/`）

`GLAbstraction` 补：

```java
/** 创建一个缓冲对象。与 createVbo 分开是因为用途不同（这个要绑 SSBO 靶子）。 */
int createBuffer();

/** 绑定到 GL_SHADER_STORAGE_BUFFER。 */
void bindShaderStorageBuffer(int buffer);

/** 分配（或重新分配）缓冲存储，usage 用 GL_DYNAMIC_COPY。 */
void allocateBufferStorage(long sizeBytes);

/** 写到缓冲的指定偏移。 */
void uploadBufferSubData(long offsetBytes, ByteBuffer data);

/** 绑到某个 SSBO 绑定点（glBindBufferBase）。 */
void bindBufferBase(int bindingIndex, int buffer);

void deleteBuffer(int buffer);
```

`FakeGLAbstraction` 要跟上——**并按「按需放开」的既有纪律**，
这些方法在单测里有没有消费者由实现时决定；**没有消费者的不要放开**（见 Task 1 的先例）。

### 4.3 FFT 计算核（`gpu/`）

**一个 compute shader 干完一件事**：加窗 → 位反转 → `log2(N)` 级蝶形 → 取幅度 → 写输出。

关键决策与理由：

**① 单 workgroup，全部在 shared memory 里做。**
`local_size_x = 1024`，`barrier()` 分隔各级。

- **这样位反转就在着色器内部发生**（第一步），**不依赖任何外部步骤**——直接避开 §3.3 缺陷③。
- 免去 `log2(N)` 次 dispatch 与 `glMemoryBarrier` 的 CPU 开销（GPUFFT 是每级一次 dispatch）。
- **代价**：shared memory 要放得下 `2 × N` 个 float。N=4096 时是 **32 KB**，
  在常见的 48 KB 上限之内；**N=8192 就是 64 KB，超了**。**所以本规格的 N 上限是 4096。**

**② uniform 一律声明成 `int`，与 `glUniform1i` 配对。**
这是 §3.3 缺陷②的直接教训（同一个坑 ② 在 `uPickId` 上也踩过）。
**不许声明 `uint` uniform**——`ShaderProgram` 只有 `glUniform1i`，对 `uint` 用它会
`GL_INVALID_OPERATION` **且值不生效**。

**③ 不许用 GLSL 保留字当标识符。**
这是缺陷①的教训（`half`）。**实现时用 `halfLen` / `halfN` 这类名字**。
并且**校验器里要有一条"着色器编译成功"的断言**——否则失败会晚到很久才暴露。

**④ 归一化与窗增益补偿必须做对。**
- 未归一化的 DFT 峰值是 `N/2`（实余弦的两个共轭峰各占一半）
- 各窗的**相干增益**：矩形 ×1、Hann ×2.013、Hamming ×1.862、BH ×2.805
  （数值来自参考项目 `FFTFilter.cpp:204-223`，**但本规格要求实现时自己验算一遍**，
  见 §10 R4）
- **换窗不改变幅度读数是产品要求**，不是优化

### 4.4 `ChartType.SPECTRUM`（`chart/` 的唯一改动）

**这是本规格唯一破"`chart/` 冻结"这条规矩的地方**，因此要说清为什么值得：

- 频谱**本质上是一类图型**（x 轴是频率、数据是幅度），不是"折线的一种画法"。
- 做成 `ChartType` 成员之后，它**被 `ChartRenderer` 正常调度**：拾取、z 序、`Layer` 分组
  **全部免费**——与当初"② 的数据走 instancing"是同一类判断：**让新东西长在已有机制上**。
- **它不破任何边界**：`ChartType` 加一个常量，`chart/` 仍然零 GL 依赖，
  `ChartPackageIsolationTest` 照样通过。

```java
    /** 频谱：数据是频域幅度，由 GPU 上的 FFT 算出（③-1）。 */
    SPECTRUM(Flag.SPECTRUM),
```

`polylineFamily()`（`connectsSamples() || drawsMarkers() || drawsBars()`）**返回 false**
——与热力图/瀑布图同类：**它不是"同一套顶点怎么画"的问题，是"顶点怎么来"的问题**
（`ChartType` 的类文档已经把这条边界写死）。

### 4.5 渲染：**复用 ② 的实例化机制**

FFT 的产物是「N/2+1 个幅度值」，**与折线的线段数据同构**（都是每实例若干 float）。
所以：

```
采集环形缓冲（既绑 SSBO 又绑 VBO）
      ↓  单一 compute dispatch：加窗 → 位反转 → 蝶形 → 幅度
FFT 输出缓冲（同样既绑 SSBO 又绑 VBO）
      ↓  ② 的实例化绘制（baseInstance / 双偏移属性 / 拾取 pass 全部照用）
频谱曲线
```

**「同一个缓冲既绑 SSBO 又绑 VBO」是关键**：缓冲对象本来就可以绑到多个靶子上，
`glVertexAttribPointer` 记录的是**调用时绑在 `GL_ARRAY_BUFFER` 上的那个缓冲**，
与 SSBO 绑定互不干扰。**因此 compute 写完不需要任何 GPU 侧拷贝。**

## 5. 数据流与坐标系

```
时域样本（环形缓冲，float32，每点 4 字节）
   ↓ 取最近 N 个（可能跨环绕 → 着色器里用 & (cap-1) 取模）
   ↓ 加窗
   ↓ 位反转 + 蝶形
   ↓ 幅度 = sqrt(re² + im²) × 归一化 × 窗增益补偿
N/2+1 个幅度值（线性），写进输出缓冲
   ↓
② 的折线渲染器按"bin 索引"当 x 画出来
```

**坐标约定（钉死）**：

- **x = bin 索引**（0…N/2），等间隔 → **与 `ChartRenderLayout.screenX(索引)` 天然一致**，
  不需要新的映射。x 轴的窗口单位是 **bin**；要显示成 Hz 由应用自己换算轴标签。
- **y = 幅度**。计算产出**线性幅度**；**dB 在显示层做**（§6.4）。
- **DC 在 bin 0**（参考项目同样如此：`cap->m_triggerPhase = 0`，注释 `//first peak is DC`）。

## 6. 参数与默认值

### 6.1 FFT 长度

**固定可配，2 的幂，512 / 1024 / 2048 / 4096，默认 2048。**

- **不跟参考项目的 `FFTFilter`（用整段采集）**——那是"采集→分析"的单次触发模型，
  **不是实时绘图**。
- 默认 2048 → 1025 个 bin，与 2000 像素宽的屏幕大致匹配。512 只有 257 个 bin，
  每个 bin 摊 8 px，太粗。
- **上限 4096** 是共享内存约束（§4.3 ①）。

### 6.2 窗函数

**矩形 / Hann / Hamming / Blackman-Harris，默认 Blackman-Harris。**

**默认 BH 而不是参考项目 FFT 的 Hamming**：示波器场景常要在**大载波旁边看小谐波**，
BH 的旁瓣是 −92 dB，Hamming 只有 −43 dB。**旁瓣高看起来像"底噪抬起来了"，不像 bug。**

### 6.3 窗增益补偿

**必须做**，否则换窗就换读数。系数：矩形 ×1、Hann ×2.013、Hamming ×1.862、BH ×2.805。

> **这些数值来自参考项目，本规格要求实现时自己验算一遍**——理由见 §10 R4，
> 那份代码有一个被测试掩盖的窗函数 bug。

### 6.4 幅度映射

**计算产出线性幅度；显示层可选线性或 dB。**

- **不用把 dBm@50Ω 焊死在计算里**——JFGL 是通用图表框架，50 Ω 是示波器约定。
- **但显示层的默认是 dB，参考值默认 50 Ω dBm**（`10*log10(功率)+30`），
  默认视图 **0 dBm 顶 / −70 dBm 底**——**默认伺候驱动场景，但不焊死**。
- 参考值可配（dBFS / dBm@其他阻抗 / 任意参考）。

## 7. 测试策略

沿用本项目纪律：**纯计算的写单测，需要 GL 的写像素校验器，两者都要变异验证。**

### 7.1 单元测试（不需要 GL）

| 测试类 | 覆盖 |
|---|---|
| `FftParametersTest` | N 的合法值、窗枚举、**窗增益补偿系数**（逐个与手算值比）、归一化因子的算式 |
| `SpectrumLayoutTest` | bin 索引 → x 的映射与 `ChartRenderLayout` 一致；dB 映射的端点与参考值 |

**窗函数与归一化是纯算术**，可以脱离 GL 穷举——**这一段必须单测**，
因为它是"数值对不对"的唯一低成本守卫（见 §10 R4）。

### 7.2 像素校验器 `FftVerifier`

**`GpuFftVerifier` 已经存在**（`adab313`，897 行），它现在**预期是红的**（退出码 1）——
它测的是旧 `GPUFFT`，记录的是那三层缺陷。

**做法：把它改造/更名为 `FftVerifier`，改为测新核。**

> **为什么不新写一个、把旧的留着当记录**：**一个预期永远红的校验器是负债**——
> 人一旦习惯"它红是正常的"，它就再也不起 gate 的作用了。
> `GPUFFT` 那三层缺陷的记录**已经落在两处不会腐烂的地方**：`CLAUDE.md` 的「未实现」一节，
> 以及提交 `adab313` 自身。校验器里只需在文件头留一句指回它们的说明。
>
> **改造时保留它已经证明有效的那几条判据**——尤其是"与 CPU 参考逐 bin 比对"
> 与"一个最小 kernel 只换 uniform 类型"的对照实验（那条把 §3.3 缺陷②钉死了）。

**核心判据（唯一能把"对"与"错"分开的）**：

1. **已知频率的纯正弦 → 峰值必须落在正确的 bin。**
   `N=2048`，取 `k0 = 100`（既非 0 也非 N/2，且不在任何"对称位置"）。

   **期望：`|X[k]|` 在 `k=100` 处有唯一的峰，其余远小于它。**

   > ⚠️ **注意：不要去找 `k = N-100 = 1948` 那个共轭峰**——**本规格的输出只有
   > `N/2+1 = 1025` 个 bin**（§5），实余弦的共轭峰在半谱里**被折叠掉了**。
   > 只有做全复数谱输出时才会看到它（`GpuFftVerifier` 测旧 `GPUFFT` 时用的是
   > `N=64` 的完整输出，所以那里 `k=7` 与 `k=57` 都在——**那是另一回事，别照抄**）。

   **三个频率各跑一次**（低/中/高，例如 100 / 400 / 900）——多个频率都错位比
   "某一个错"更能说明是系统性的。**三个都必须 `< N/2`**，否则落在折叠区外。
2. **与 CPU 参考 DFT 逐 bin 比对**（N 小时 `O(N²)` 可接受；N=2048 时用 CPU FFT）。
   **只断言峰值位置的话，一个整体缩放错的实现照样能通过。**
3. **换窗不改变幅度读数**：同一个正弦用三种窗各跑一次，**峰值幅度在容差内一致**。
   这条直接钉住 §6.3——**没有它，窗增益补偿写错不会有任何症状**。
4. **着色器编译成功**（§4.3 ③ 的教训：缺陷①让失败晚到很久才暴露）。
5. **DC 行为**：常输入（全部相同的值）应当在且仅在 bin 0 有峰。

**变异验证（至少四条）**：

| 变异 | 期望失败的断言 |
|---|---|
| **去掉位反转**（直接删掉那一段） | 峰值位置断言（**这正是 `GPUFFT` 的缺陷③**） |
| 把某个 uniform 声明成 `uint` | 着色器编译或值不生效（**缺陷②**） |
| 去掉窗增益补偿 | "换窗不改读数" |
| 归一化因子错一倍 | 与 CPU 参考的逐 bin 比对 |

### 7.3 校验器的场景必须会变

`PickVerifier` 出过一次真实盲区：**24 条断言全绿，却漏掉一个真缺陷，因为场景每帧完全相同**。

`FftVerifier` 至少要有：**输入频率中途改变**（断言峰值跟着移动）、
**幅度中途改变**（断言峰值高度跟着变）。

## 8. 错误处理

| 情况 | 行为 |
|------|------|
| `N` 不是 2 的幂 / 超过 4096 / 小于 256 | **构造时抛** `IllegalArgumentException` |
| 源数据不足 N 个样本 | **明确报错**，不补零——补零会**改变频谱**（那是 zero-padding，是另一个特性），静默补零会让用户看到一条"看起来正常"的错谱 |
| 着色器编译失败 | `ShaderProgram` 的构造已经会抛 ✓ |
| 源系列不是流式数据 | **明确报错**（FFT 要的是连续样本） |

## 9. 已知风险

**R1：N 上限 4096 是共享内存硬约束。** 要更大必须改成多趟（两级归约或 Stockham 乒乓），
那是 ③-1b。**4096 个 bin 对 2000 px 的屏幕够用**，所以本期不做。

**R2：单 workgroup 吃不满 GPU。** N=2048 时只有 1024 个线程、一个 workgroup，
**其余 SM 空转**。这是"一次 dispatch 换简单"的代价。
若实测发现它是瓶颈，改法是**多个频谱并行**（每个系列一个 workgroup）而不是拆 N。
**先实测再优化**——不要凭"三个 SM 空着"就动手。

**R3：跨环绕取样本。** N 个样本可能跨过环的接缝，着色器里要 `& (cap-1)` 取模。
**这与 ② 的槽位镜像是同一类问题**——② 在那里踩过一次（槽位 0 的镜像没写，
产出"掉到 0 的假信号"）。**实现时要专门为跨环绕造一个断言。**

**R4：⚠️ 参考项目的窗函数系数不可全信。** 它有一个**被测试掩盖的 BH 窗公式 bug**
（§3.4）。所以：

- 窗系数**必须自己验算**（教科书值 vs 参考值）
- **绝不允许把参考项目的黄金模型直接抄进测试**——那正是它掩盖 bug 的方式
- 判据要用**独立的物理量**：例如"加窗后信号的功率应当等于原信号功率乘以窗的功率增益"

**R5：幅度归一化的两套约定。** 参考项目 `FFTFilter` 用 `sqrt(2)/N`、
`Spectrogram` 用 `2/N`，**两条路径差 3 dB**（这是读代码的推论，未运行验证）。
**本规格只允许一种约定**，并在单测里钉死。

**R6：算力预算未实测。** N=2048 的一次 FFT 在这台机器上要多久，**目前是未知数**。
它是"能不能每帧跑一次"的前提。**实现时第一件事就是测它**，不要等做完了才发现超预算。
